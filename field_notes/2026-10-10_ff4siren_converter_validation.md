# FF4SIREN as a converter validation case

The user's objective is to discover defects in vgm2mml's generated MML and PCM
IR. Reference compilation is a prerequisite for separating converter defects
from tool/input compatibility, not completion of converter validation.

## What is established

- Original FF4SIREN MML through the existing native MXC adapter reproduces the
  reference MDX exactly, including mdxinfo content fields.
- Its PDX was reused unchanged. No PCM IR was generated by that trial and no
  PDX generation method was validated by copying that PDX.
- Neither original-to-generated NOTE equivalence nor MML/PCM IR correctness
  through vgm2mml has been demonstrated for FF4SIREN.
- Current combined PCM generation still compiles FM through mmlx. The validated
  native MXC baseline has not yet been integrated into that production route.

## Proposed comparison, not yet executed

```text
reference MML + MDX + PDX
        |                         |
        | checked VGM capture     | direct reference analysis
        v                         v
     input VGM              expected notes/sample bindings/metadata
        |
     vgm2mml --dump-passes
        |
   generated FM MML + neutral PCM IR + target plan
        |
   validated compilation and independently checked PDX packing
        |
   generated MDX + PDX -------- compare with reference evidence
```

Before using a captured VGM as the input baseline, check its note/gate timing,
PCM sample supplies, starts, holds and stops against direct reference evidence.
The currently known-problematic soundlog PCM conversion is not an oracle. Do
not repair unrelated replay tools as part of this task. If capture correctness
cannot be established, retain that comparison as unverified and separately
perform the static MML/MDX and sample/PDX checks that have independent evidence.

Use the proven native MXC path as the FM compilation baseline for generated MML
validation. Validate PCM IR-to-PDX separately: pack samples from the actual IR,
then independently inspect each populated offset/length, encoded bytes and its
binding to PCM notes. Reference PDX copying cannot substitute for this check.
Adapting the production combined route requires a separate reviewed change;
the user's implementation pause remains in force.

## note.x compiler and decoded note-event comparison

The user's "NOTE" question is interpreted from the preceding discussion as
referring to the `note.x` compiler named in RAY2C, rather than only to note
events. Recompiling RAY2C with the intended note.x tool and comparing its MDX
would establish a second tool/dialect baseline. That tool has not been verified
locally and this trial has not been performed. It is useful for extending
reference coverage, but does not need to precede the FF4SIREN converter trial:
FF4SIREN already has a verified native MXC compilation baseline.

Independently of the compiler question, musical note-event comparison is needed
to test generated MML and PCM projection.

Compare decoded/expanded musical events, retaining their original command
positions and target clock. Inspect original and generated structures as well
as expanded event timing; aggregate note/command counts alone cannot establish
equivalence.

- FM: pitch/detune, note onset, duration, actual gate/key-off boundary,
  retrigger versus hold/tie, rests, instruments, volume/pan and loop structure.
- PCM: referenced sample bytes/range, onset, duration, hold versus restart,
  release/stop intent, rate/pan and loop/ending structure. Keep source reset and
  continuation evidence distinct from projected NOTE/hold commands.
- Shared timing: FM/PCM clock, ordering of coincident events and loop boundary.
- Metadata/container: title/PDX name raw bytes and mdxinfo fields, valid PDX
  offset/length table and resolution of the intended PDX.

The current PCM target explicitly does not emit source song loops. FF4SIREN's
reference PCM track loops, so complete loop-structure equality would encounter
that known target gap. Preserve source loop evidence and report this as a
known projection difference; it is not proof of a malformed PCM source IR.
Do not call finite-prefix agreement a complete round-trip pass.

Finding locations are attributed separately: VGM capture, source analysis/PCM
IR, MDX projection/MML, tool adapter/compiler, and PDX packing. Static NOTE and
container equality provide evidence about generated data; native MMDSP display
and terminal PCM stopping still need their own confirmation after a candidate
is generated. No reference playback problem has been asserted.
